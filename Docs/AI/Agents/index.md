# AI Agents

[Deutsch](../../Translations/de/AI/Agents/index.md)

An agent is the functional unit that receives a prompt and generates a response from the LLM. In the configuration, an agent consists of two levels:

- `AI_AGENT` describes the agent's stable identity, such as its name, alias, description, and app assignment.
- `AI_AGENT_VERSION` describes a specific executable version of that agent, such as its prototype, LLM connection, instructions, and `CONFIG_UXON`.

This allows an agent to have multiple versions. Calling components use the agent alias and, optionally, a version constraint. The factory then selects the appropriate enabled version. New prompts, tools, or concepts should therefore be maintained as new agent versions whenever behavioral changes need to remain traceable.

## Task handlers and MCP endpoints

`AiTaskHandlerInterface` contains the shared identity, Workbench and tool-host behavior. Regular AI
agents extend it through `AiAgentInterface` and add prompts, conversations and model connections.
The `McpServer` prototype is a task handler but not an AI agent: it exposes configured tools without
pretending to handle prompts or requiring an LLM connection.

Use `axenox/genai/AI/Agents/McpServer.php` as `PROTOTYPE_CLASS` for MCP endpoints. Tools can be
configured directly in `CONFIG_UXON` or contributed by skills assigned to the endpoint version.
Skill instructions, skill concepts and model connections are not loaded for this prototype.

See the [MCP configuration reference](../../MCP/index.md#conversation-logging-and-grouping) for
conversation grouping, inactivity timeouts, development mode and client chat identifiers.

## Shared conversation history

Agents and MCP endpoints use the same authorized conversation log, bound to the exact handler
version and authenticated user. `TYPE` distinguishes `agent` from `mcp`; `TOPIC_ID` is only an
external correlation identifier, never an access credential. Development mode is persisted
independently of the model connection. Test runs and disabled agent versions default to
development mode; an explicitly supplied setting takes precedence.

Each received tool batch creates one `tool` message before execution and enriches that same
message with typed results afterward. Individual calls are available for drill-down before the
batch finishes, with `IN_PROGRESS`, `SUCCEEDED`, or `FAILED` states. A missing completion time
means **completion not recorded**, not failed execution or permission to retry. Manual refresh
is sufficient to see updated details.

Every connector submission uses a fresh query built from the active messages of the conversation
(`getMessagesActive()`). Messages always pass through the conversation: tool results saved there are
automatically part of the next query. Prior instructions, user messages, assistant content, completed
tool rounds and attachments are restored from storage without invoking historical tools.

**Any conversation can be continued with any supported API** - e.g. after an administrator switched
the LLM connection of an agent. API adapters degrade instead of refusing and add a warning to the
conversation:

- attachments the target API cannot accept, and historical attachments that cannot be loaded anymore,
  are replaced by a short note like *"[photo.heic was attached but cannot be sent to this model]"*,
- tool batches without results (e.g. interrupted runs) are omitted - calls and results together,
- call IDs the API does not accept are replaced by safe unique IDs within the request.

Unfinished answers (token limit, paused turn) keep their text and are saved with the finish reason
`truncated`. The runtime never reruns tools to repair history.

Attachments of user messages are sent natively where the API supports them: JPEG, PNG, GIF and WebP
images for all three APIs, PDF for Responses and Claude, plain text for Claude. The Responses API also
accepts text and code files, Word, RTF and OpenDocument texts, PowerPoint presentations and Excel or CSV
spreadsheets. Other types become a note. Files generated by a
model (e.g. images of the Responses API) are saved as attachments of the response like user
attachments.

LLM usage belongs only to messages representing LLM responses. MCP calls do not manufacture
model names, tokens or cost. Tool errors remain deliverable results, with correlated standalone
error entries for inspection. Each tool warning also creates a correlated standalone `warning`
message, without error feedback or an error log ID. Warning-only results remain successful unless
the call was rejected.
Operational logging or delivery errors do not change a tool's execution outcome.

Warning and error counters count only separate messages with the corresponding role, never
diagnostics embedded in tool-result JSON. Existing separate diagnostic messages remain counted;
warnings retained only in JSON are not backfilled automatically. History migrations retain result
errors and warnings for replay, not for counter calculation.

Run history migrations with conversation writers stopped. Reliably matched legacy tool-request
and result pairs become one row: the result UID and `MESSAGE` stay unchanged, while `DATA`
receives ordered calls and string results. Original rows and payloads are retained under
`DATA.legacy`; linked call details and LLM usage move to the result row before the request row is
deleted. Other message text stays unchanged. Sequence numbers are normalized and made non-null
and unique; already-advanced allocation counters never decrease.

Missing results, invalid arguments, malformed JSON or ambiguous usage leave the affected pairs
untouched. The migration neither invents results nor reruns tools; such incomplete batches are
omitted from the model context when the conversation continues. Continuation requires the original
handler version.

For PHP consumers, `AiResponse::getConversation()` exposes the shared history and
`AiResponse::getMessages()` contains only entries generated for that response turn.
`AiFactory::createConversation($handler, $conversationId, $row)` accepts an
`axenox.GenAI.AI_CONVERSATION` DataSheet row keyed by attribute aliases such as `TYPE`,
`DEVMODE`, `TITLE` and `CONNECTION`. New rows require `TYPE`; omitted `DEVMODE` defaults to false.
`DATA`, when supplied, must already be JSON. The handler, version and authenticated user
are assigned internally. When restoring by ID, only the supplied `TYPE` is checked;
other row values do not overwrite stored metadata.
Tool messages implement `AiToolCallMessageInterface`: iterate their ordered `getCalls()` and
call-ID-keyed `getToolResults()`. Results retain their complete value and ordered
`getErrors()` / `getWarnings()` even after restoration; exceptions are fresh-only.

### Messages, queries and API adapters

Each component has a clear responsibility, so that adding an API or a message type does not
require changes elsewhere:

| Component | Responsible for |
|---|---|
| `AiConversation` | The only component that saves and loads messages, attachments, tool call details and opaque adapter data, including legacy history. Selects the active model context. |
| `AiMessageInterface` and subtypes | Provider-independent facts about one message: context role, text, attachments, tool calls and results. |
| Agent | Saves prompts and responses through the conversation, builds queries, runs tools. |
| `AiQueryInterface` | One exchange with the LLM: selected messages, request settings, the response message, usage and warnings. |
| Request adapter | Derives its API request from the messages and settings of a query. |
| Response adapter | Derives a generic message, finish reason and usage from its API response. |

API adapters never use message types. Every message tells them its **context role** via
`isInstructions()`, `isInput()` or `isOutput()`; messages where all three return false (e.g.
warnings and errors) are for designers only and never sent to an LLM. Tool calls are output
messages implementing `AiToolCallMessageInterface`. A new message type therefore needs a constant
and label in `AiMessageTypeDataType` and a message class - but no adapter changes.

`getText()` returns the model context - always text. A structured answer is the JSON text produced
by the LLM. `toMarkdown()` is a separate designer-facing representation, which is saved in the
`MESSAGE` column. For responses, `MESSAGE` shows the answer the way the agent presents it (e.g.
extracted via `response_answer_path`), while the full answer is restored from `DATA`.

Response adapters report generic values only: finish reasons are constants of
`AiFinishReasonDataType` (`completed`, `tool_calls`, `truncated`, `refused`, `error`), usage is
reported via the query (tokens, model, cost). Citations become a list of sources, refusals become
text, unsupported content is dropped with a warning. Tools executed by the provider itself (e.g.
built-in web search) are already reflected in the answer text.

An adapter may keep optional **adapter data** with a response message, e.g. OpenAI reasoning items
or signed Claude thinking blocks. The conversation saves it as an opaque value. Only the owning
adapter reads it - and only if it was produced by the current model and still matches the generic
message. Otherwise the request is built from generic messages alone, exactly as if the data had
never existed. Older `provider` data in `DATA` is ignored.

The `DATA` format and all legacy formats are handled by the internal `AiMessageSerializer`, which
only `AiConversation` uses. Adapters, agents and queries never read `DATA`.

To add an API, implement a request adapter (`HttpRequestAdapterInterface`) and a response adapter
(`HttpResponseAdapterInterface`) and select them in the connector. Use the provider-independent
helpers of `ConversationApiAdapterTrait` and create response messages with
`AiFactory::createMessage()` or `AiFactory::createToolCallMessage()`. Nothing else needs to change.

## Structure of an agent version

An agent version defines how the agent is created at runtime:

- `PROTOTYPE_CLASS` points to the agent's PHP class, for example `axenox/genai/AI/Agents/GenericAssistant.php`.
- `DATA_CONNECTION`, or the default connection, determines which AI connector or model is used.
- `INSTRUCTIONS` contains the system prompt. It can include Markdown and placeholders.
- `CONFIG_UXON` is the structured configuration model for the prototype. For `GenericAssistant`, it is used to import tools, concepts, the response schema, and other prototype properties.

The prototype implements the behavior in PHP. The UXON model provides the specific configuration for a version. This allows the same prototype to be reused for multiple agents or versions.

## Role of `CONFIG_UXON`

`CONFIG_UXON` is not a second prompt. It is the machine-readable configuration of the agent prototype. When a version is loaded, the UXON is read from `AI_AGENT_VERSION.CONFIG_UXON`. The version's name, alias, and `INSTRUCTIONS` are then added to this UXON, which is used to instantiate the configured prototype.

A typical excerpt looks like this:

```json
{
  "tools": {
    "GetObject": {
      "description": "Load information about a metaobject.",
      "arguments": [
        {
          "name": "object_alias",
          "data_type": { "alias": "exface.Core.String" },
          "description": "Fully qualified object alias or UID"
        }
      ]
    }
  },
  "concepts": {
    "sitemap": {
      "alias": "axenox.GenAI.AppDocsConcept",
      "depth": 0,
      "app_alias": "exface.Core",
      "starting_page": "sitemap.md"
    }
  }
}
```

The property names in the UXON correspond to the prototype's configurable properties. For `GenericAssistant`, the most relevant properties include `tools`, `concepts`, `response_json_schema`, and other documented UXON properties. Skills are assigned separately to the agent version and are not stored in `CONFIG_UXON`.

## Instructions and concepts

Concepts are placeholders that dynamically generate parts of the system prompt. They are maintained under `concepts` in the UXON. The key is the placeholder name used in the instructions.

Example:

```json
{
  "concepts": {
    "introduction": {
      "alias": "axenox.GenAI.AppDocsConcept",
      "depth": 0,
      "app_alias": "exface.Core",
      "starting_page": "Getting_started/introduction.md"
    }
  }
}
```

The concept can then be included in the instructions:

```md
## Introduction to the platform

[#introduction#]
```

At runtime, the agent first renders the concepts and replaces the placeholders in the prompt. Concepts are suitable for context generated from data, documentation, the metamodel, or tool output. Some concepts can also provide their own tool models; during rendering, these are added to the agent's tool configuration.

## Configuring skills

Skills are reusable, non-versioned configurations assigned in the skill list of an agent version. Their instructions are appended to the system prompt after the agent instructions, and their tools are made available automatically. See the [skill reference](../Skills/index.md) for configuration, nested skill placeholders, and collision rules.

## Configuring tools

Tools are maintained under `tools` in `CONFIG_UXON`. The key is the function name that the LLM can use later. A tool definition describes at least its purpose and arguments. A specific tool prototype can optionally be selected via `alias` or `class`. Without an explicit selector, the factory attempts to find the tool prototype by its function name.

Example:

```json
{
  "tools": {
    "GetLogEntry": {
      "arguments": [
        {
          "name": "LogId",
          "data_type": { "alias": "exface.Core.String" },
          "description": "The Log-ID visible to the designer"
        }
      ],
      "description": "Read the log entry for a visible Log-ID."
    }
  }
}
```

The description should clearly tell the LLM when to use the tool and which values are permitted. Arguments should have names, data types, and descriptions that are as specific as possible.

## Building an agent

1. Create the agent in `AI_AGENT` and define its alias, name, description, and app assignment.
2. Create the first version in `AI_AGENT_VERSION`.
3. Select an appropriate `PROTOTYPE_CLASS`, usually `GenericAssistant` for chat assistants.
4. Configure the LLM or data connection.
5. Write the instructions and add the required concept placeholders.
6. Configure concepts in `CONFIG_UXON` and match the placeholder names to those in the instructions.
7. Assign reusable skills in the agent version's skill list; their instructions and tools are included automatically.
8. Configure tools in `CONFIG_UXON` if the agent needs to actively load data or prepare actions.
9. Test the agent with test cases and conversation logs, and maintain improvements as new versions.

## Versioning

Versions make agent behavior reproducible. A new version is appropriate when instructions, tools, concepts, the response schema, or the model connection change in ways that may affect existing tests or production responses.

When loading an agent, the factory retrieves all of its versions, sorts them in descending order, and selects the best match for the requested version constraint. If a version has no connection of its own, it can inherit one from a previous version. Nevertheless, the version currently used by a production agent should be clearly documented.
